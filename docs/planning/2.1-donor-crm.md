# Module Plan — 2.1 Donor & Partner Database (CRM)

Status: **planning, pre-UI-rework**. Stage per AGENTS/CLAUDE.md process: build clickable mockup → demo to DORA → written sign-off → only then Prisma + backend. This doc covers the mockup stage only.

## Source of truth

`docs/drmp_proposal.tex`, Section 2.1 (`\label{sec:crm}`, lines 99–106):

- Searchable database of donors/prospective partners: individual donors, alumni, companies, foundations, PSUs, other prospective partners.
- Per-record profile: contact details, category/type, relationship owner (DORA staff member managing the relationship), donor interests/areas of giving interest, source of lead (referral, event, alumni network, inbound enquiry), free-text notes.
- Relationship-management fields: engagement stage (`Prospect / Engaged / Solicited / Committed / Active Donor / Lapsed`), date+summary of last interaction, next action + due date, contribution history, repeat-donor status (derived from contribution history), links to donor's pipeline opportunities (2.2) and proposals (2.3).
- Data source constraint: only DORA-provided or DORA-staff-entered data — no scraping/purchasing/importing third-party contact DBs (Section 2.21).

| Links to proposals (2.3) | 2.3 not started | add `proposalIds: string[]` placeholder; detail page shows empty-state section |

## Mock data model changes (`src/lib/types.ts`, `src/lib/mock-data.ts`) — mockup only, no Prisma

- `DonorType`: add `"PSU" | "Other"`.
- `EngagementStage` (rename from `DonorStatus`): `"Prospect" | "Engaged" | "Solicited" | "Committed" | "Active Donor" | "Lapsed"`.
- `Donor.leadSource`: `"Referral" | "Event" | "Alumni Network" | "Inbound Enquiry" | "Other"`.
- `Donor.interests: string[]`.
- `Donor.notes: string`.
- `Donor.nextAction?: { description: string; dueDate: string }`.
- `Donor.contributions: { id, date, amount, purpose }[]`; drop stored `totalGiving`, compute at render time.
- `Donor.repeatDonor`: computed (`contributions.length > 1`), not stored.
- `Donor.proposalIds: string[]` (stays empty — no proposals exist yet).
- `PipelineOpportunity.donorId: string` replacing name-based link; keep `donorName` as convenience display field synced from the donor record.

## Screens

1. **List** (`/staff/donors`) — filters: type, engagement stage, relationship owner; search by name/email.
2. **Detail** (`/staff/donors/[id]`) — profile card; engagement fields incl. next action; contribution history table + derived repeat-donor badge; linked pipeline opportunities (from `donorId` reverse lookup); linked proposals section (empty state, since 2.3 doesn't exist); interaction log + "log interaction" action (existing `logInteraction` stays).
3. **Create donor** — form covering all fields above; mark fields required vs optional per open questions below.
4. **Edit donor** — same form, update path.

## Role gating (display-only until backend; matches `.claude/rules` — real enforcement is a Phase-I-backend concern, not this stage)

- `FUNDRAISING_OFFICER`: create, edit, log interaction.
- `DEAN_APPROVER`: same edit rights per CLAUDE.md ("only FUNDRAISING_OFFICER and DEAN_APPROVER carry real permission logic").
- Other five roles: read-only, not specially gated (per "don't gate Phase I UI on the other five").
- Reuse `canEditDonor` from `donors-actions.ts`, update it to the two-role check above (currently allows those two already — keep).

## Guardrails specific to this module

- No import / bulk-upload / "enrich from web" affordance anywhere in the UI — Section 2.21 is a workflow constraint, not just a backend rule.
- No Prisma model, no route handler, no persistence beyond `store.tsx` — reset-on-refresh is expected and fine at this stage.
- Don't touch `/staff/endowment-funds` or `/staff/csr-grants` (Phase II demo, out of bounds).
